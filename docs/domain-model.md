
# Domain Model

## 1. Purpose

This document defines the business domain, core business capabilities, service boundaries, and ownership model for the TaskFlow Platform.

The objective is to establish a clear understanding of the problem domain before implementation begins. This ensures that each microservice has a well-defined responsibility, minimizes coupling, and supports independent development and deployment.

The domain model is technology-agnostic. It focuses on business concepts rather than implementation details.

---

# 2. Business Overview

TaskFlow Platform is a collaborative project management application that enables organizations to manage projects, teams, and tasks.

The platform allows users to:

- Register and authenticate securely
- Create and manage organizations
- Create projects
- Organize project members
- Create and assign tasks
- Track task progress
- Add comments and attachments
- Receive notifications for important events

The system is designed using a microservices architecture where each service owns a specific business capability.

---

# 3. Business Objectives

The primary objectives of the platform are:

- Centralize project management
- Improve collaboration between team members
- Track project progress
- Maintain task ownership
- Provide secure authentication and authorization
- Support future scalability through independent services

# 6. Core Business Entities

The platform is built around the following business entities:

## Organization

Represents a company or workspace.

Contains:

- Organization Name
- Description
- Owner
- Members
- Projects

---

## User

Represents a registered platform user.

Contains:

- User Identifier
- Name
- Email
- Profile Information
- Preferences

Authentication credentials are managed separately by the Auth Service.

---

## Project

Represents a collection of work within an organization.

Contains:

- Project Name
- Description
- Status
- Members
- Tasks

---

## Task

Represents an individual work item.

Contains:

- Title
- Description
- Priority
- Status
- Due Date
- Assignee

---

## Comment

Represents communication related to a task.

Contains:

- Message
- Author
- Timestamp

---

## Notification

Represents a user notification generated by business events.

Contains:

- Recipient
- Notification Type
- Message
- Delivery Status

---

# 8. Data Ownership

Each business entity has a single owning service.

| Data | Owning Service |
|------|----------------|
| Credentials | Auth Service |
| User Profile | User Service |
| Organization | Project Service |
| Project | Project Service |
| Task | Task Service |
| Comment | Task Service |
| Notification | Notification Service |

No service may directly access another service's database.

Cross-service communication must occur through REST APIs or Kafka events.

---

# 9. Communication Model

## Synchronous Communication

REST APIs are used when an immediate response is required.

Examples:

- User login
- Fetch project details
- Retrieve task information

---

## Asynchronous Communication

Kafka is used to publish business events.

Examples:

- User Registered
- Project Created
- Task Assigned
- Task Completed
- Comment Added

Consumers subscribe to these events independently.

# 11. Domain Principles

The platform follows these domain principles:

- Every service owns a single business capability.
- Every entity has a single source of truth.
- Services communicate through contracts rather than shared databases.
- Business events are immutable.
- Domain logic remains within the owning service.
- Services are independently deployable.
